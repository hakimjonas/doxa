## Fuel desugaring status (0.8.2 work)

### What works

`_replaceSelfCalls` — the AST walker that replaces self-recursive calls
`f(e1, e2)` with `f_fuel(fuel_, e1, e2)`. Handles all SExpr kinds:
SLamKind, SMatchKind, SAppKind, SLetKind, SPiKind, etc. Proven correct
on simple test cases.

### What's blocking

The zero-fuel branch in the generated `match fuel { case zero => ??? }`
must produce a value of the function's return type, but has no value
available. The return type depends on function parameters that the zero
branch cannot produce. This is a type-theoretic problem, not a code bug.

For `strong_ind_impl : P n`, the return type is `P n` (Prop), and the
zero branch has no `P n` value. Using the original body in the zero case
type-checks for `Nat`-returning functions but fails for `Prop`-returning
functions.

### Possible solutions

A. **Pass a `default` parameter** — the generated `f_fuel` takes an
   extra `default: T` parameter for the zero case. The wrapper passes
   a dummy value.

B. **Use `False.rec`** — for Prop-returning functions, the zero case
   uses `False.rec (return_type) succ_ne_zero_fuel_proof`. Requires
   a `succ ≠ zero` lemma in scope.

C. **Emit the original body unwrapped** — the zero case just returns
   the original body (which type-checks because the original function
   type-checks). This works for simple functions but fails for mutual
   blocks where the original body references other block members.

Option A is the most robust — it works for any return type.

### Mutual block issue

`strong_ind_impl` is in a mutual block (`}and strong_ind_impl_help`).
The fuel desugaring works at the `_elabFunBlock` level but requires
handling the fuel bindings in the CorecursiveGroup guard loop (skip
fuel bindings by name). Alternatively, restructure the mutual block
to standalone functions (pass `strong_ind_impl` as a parameter to
`strong_ind_impl_help`).
