## Known bugs (open work)

### 1. match-motive inference fails in deeply-nested import chains

**Symptom:** `doxa check lib/stdlib/Int/package.doxa` fails with
"match expression needs a motive in this position."

**Reproducer:**
```doxa
import "int.doxa"
```
in a standalone file also fails.

**Root cause:** `int.doxa` type-checks standalone (98 decls). When imported
through `_processImport`, some match expression inside the import chain
(possibly in `int.doxa` itself or in a transitive dependency like
`proofs.doxa`, `case_study.doxa`) lands in INFER mode without a motive.
The error is thrown at `eval.dart:2618` where `motive == null` in the
`_Infer` path for `TMatch`.

The error span is attributed to the import statement line, not the
offending match expression — a second bug in error location tracking.

**Current workaround:** `Int/package.doxa` excluded from CI type-check
via `! -path '*/Int/package.doxa'` in `.github/workflows/ci.yml`.
`int.doxa` itself is checked standalone and passes.

**Likely fix direction:** The `_processImport` function calls
`checkDeclResult` on each declaration in the imported file. If a
`fun`'s body contains a match, the `check` call should have the
expected type from the function signature, placing the match in CHECK
mode. Something in the import environment setup loses this expected
type. Compare the environment in `_processImport` vs `checkSource`.

### 2. No kernel-level `fix` for well-founded computation

**Symptom:** `gcd`, `mod`, `div` use accumulator-based structural
recursion (`*_acc` helpers). Well-founded definitions via
`termination_by` type-check but don't compute (rely on opaque
pre-seeding that produces stuck neutrals).

**Correctness implications:** Proving `gcd_comm`, `gcd_divides`, etc.
is intractable with the accumulator approach. The proofs need the
well-founded definition to be computable.

**Plan:** Lean 4's `Nat.fix` (fuel-based, computable) + `WellFounded.fix`
(noncomputable, `Acc`-based) is the right model. Doxa's `fix_by_fuel`
in nat.doxa is a first step but not auto-generated from
`termination_by`. The elaborator needs to synthesize the fuel version
automatically for single-Nat-argument `termination_by` functions.

### 3. Prop-into-Type restriction

**Symptom:** `strong_rec` cannot be built from `Nat.rec` + `Lt.rec`
because `Lt` is Prop-sorted and cannot be eliminated into Type. This is a
fundamental CIC soundness property.

**Impact:** No automatic desugaring of `termination_by` for
Type-returning functions (only Prop-returning works via `strong_ind`).

**Fix direction:** Item 2 above (fuel-based recursion) bypasses this
entirely. Fuel versions don't need `Acc` or `Lt` at all — they're
structurally recursive on the fuel counter.

## Long-term import handling concern

The import system uses a mutable global `currentImportPath` and
`importedPaths` in `elab.dart`. Import resolution chains through
`_processImport` which recursively processes declarations of the
imported file. This creates several problems:

1. **Error location:** errors in deeply-imported files are attributed
   to the top-level import statement, not the source declaration.
2. **State leakage:** `importedPaths` accumulates across the entire
   check session. If reset improperly, duplicate imports or missing
   imports occur.
3. **Recursive elaboration:** `_processImport` calls `checkDeclResult`
   internally, which means imported declarations are fully type-checked
   before the caller even sees them. The caller then calls
   `checkDeclResult` AGAIN. This double-check is intentional but fragile.
4. **Split environments:** the scratch environment in `_processImport`
   differs from the caller's environment. The classRegistry fix from
   this session exposed that `const {}` was hardcoded — three call
   sites needed fixing (`_processImport`, `checkSource`,
   `checkSourceOutput`).

**Proposed direction:** A proper import resolution API that:
- Resolves all imports up-front (transitive closure)
- Builds a single combined environment
- Processes declarations in dependency order
- Preserves error locations through the import chain
- Eliminates the mutable global `currentImportPath`/`importedPaths`
